---
FireLine's second reader of `op_identity` (Contract 6.11-0009) could decide the structure of a line but not `op-identity-bad-value`, because no corpus JSON said whether a `u8` field is a flag, an enum, a count or a dtype, what its vocabulary is, or its range. `conformance/corpus/opattrs_field_types.json` (schema `kiss-opattrs-field-types-v1`, generated by `cargo run --bin emit_opattrs_field_types` from `spec/ops.md` 6.19.2 and 6.19.3) carries per op and field: `kind` (flag, enum, count, dtype, accumulator-dtype, axis-set, vector), the enum `vocab`, the dtype `accepts` list (the float-only accumulator rule and the `matmul` integer accumulators already applied), and the range rule (axis below MAX_RANK = 8, `index_operand` below 16, `prefix_scan` exactly one axis). It is a new file: no existing corpus byte, wire byte, golden or digest moves. The generator asks the reference reader about every stated fact (every vocab token, every dtype, the flag and count spellings, each axis-set bound) and fails the build on any disagreement; that discipline fired on the first run (`gather.axis` is not 0..=255). `test_opattrs_field_types_table_is_fresh_and_complete` binds the committed file to the generator.

Also rewrites `HANDOFF.md` for the 0.19.1 state (current state, not a log; the day's one PR carries it, per the PM).
