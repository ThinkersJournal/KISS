# Where do backends say which datatypes a device computes on? (board 355, option D)

Informative. Prepared 2026-10-31 against `origin/main` b4e2ebe. CireSnave's refinement of board 355 (verbatim): "A backend is a kernel runner. Wouldn't it be the device behind the backend that limited what the backend can compute on and the kernels that specified the datatypes they can compute rather than the backend specifying a blanket dtype list? Most backends have the ability to list devices behind them, correct? When they do, do they provide information about those devices? If so, would that returned device information be the correct place for them to specify the supported dtypes?" His ruling: "355: D". Method: official vendor or Khronos pages fetched on 2026-10-31; anything I could not read is marked **UNVERIFIED** and is not a finding.

## Per backend: (1) does it list devices, (2) what says which datatypes the device computes on

| Backend | (1) Lists devices | (2) Dtype information the device returns | Form |
|---|---|---|---|
| CUDA | Yes: `cudaGetDeviceCount` "Returns the number of compute-capable devices", `cudaGetDeviceProperties` "Returns information about the compute-device", `cudaDeviceGetAttribute` "Returns information about the device" (CUDA Runtime API, Device Management) | `cudaDeviceProp` has `major` and `minor`, "Major/Minor compute capability". **No dtype field was found on that page.** Per-dtype support by compute capability is a table in the Programming Guide appendix: **UNVERIFIED** (the appendix page was not readable) | integers; the dtype set is derived from a table, not returned |
| Vulkan | Yes: `vkEnumeratePhysicalDevices` "Enumerates the physical devices accessible to a Vulkan instance" | `VkPhysicalDeviceVulkan12Features`: `shaderFloat16` ("16-bit floats (halfs) are supported in shader code"), `shaderInt8`; `VkCooperativeMatrixPropertiesKHR` (via `vkGetPhysicalDeviceCooperativeMatrixPropertiesKHR`) lists supported matrix configurations with `AType`, `BType`, `CType`, `ResultType` component types. `shaderFloat64`/`shaderInt64` in `VkPhysicalDeviceFeatures` and any bf16 feature: **UNVERIFIED** (not fetched) | per-feature booleans, plus an enumerated list of typed matrix configurations |
| OpenCL | Yes: `clGetDeviceIDs` "Query devices available on a platform" | `clGetDeviceInfo`: `CL_DEVICE_HALF_FP_CONFIG`, `CL_DEVICE_SINGLE_FP_CONFIG`, `CL_DEVICE_DOUBLE_FP_CONFIG` (`cl_device_fp_config`, "Describes ... floating-point capability"; half needs `cl_khr_fp16`, double `cl_khr_fp64`), `CL_DEVICE_EXTENSIONS` ("a space separated list of extension names"), `CL_DEVICE_OPENCL_C_FEATURES` (`cl_name_version[]`). **Reading it.** Every backend I could verify (CUDA, Vulkan, OpenCL, SYCL, HIP) has a call that lists devices and a call that returns per-device information. The per-device information is where dtype support lives where it is stated at all, but it takes **four different forms**: derived from an architecture number (CUDA), per-feature booleans and typed matrix configurations (Vulkan), floating-point config bitfields plus an extension string (OpenCL), aspect booleans (SYCL). No backend returns "the set of dtypes this device computes on" as a value. That is why a normalised KISS record is useful: it is what a provider **builds** from the native answer.

## (3) Does KISS already have a device-listing message or record?

No. `git grep -n -i -E 'device|enumerat|adapter' -- spec/announce.md` finds nothing (control: the same query on `spec/classify.md` finds `ArchSku` and the device-feature lines). Announce carries identity and a 64-bit provider capability word (§7.2); the Contract carries a per-kernel dtype set (Capabilities section); Classify carries the target token. Nothing carries a device.

## (4) The record added (KISS-ANNOUNCE §6.6)

A device-query message pair (`DVRQ` request, `DVRS` response, `DVDC` decline; FEAT bit 35) returns zero or more **device records**: opaque `device_id`; `target` token (`<ns>:<cap>`); `store_dtypes` (hold and move); `compute_dtypes` (compute on; a subset of store, the R1.32 distinction); and accuracy records keyed `(op, math_fidelity, dtype)` with a `max_ulp`. Kernels keep declaring their dtype sets in the Contract. **Effective support** for a `(device, kernel)` pair is the intersection; **effective accuracy** for `(device, kernel, math_fidelity, dtype)` is the tighter of the device's bound and the kernel's, and a kernel looser than its device's bound under the same key is declined. A reader declines a record that contradicts itself (accuracy claimed for a dtype the device does not compute on, compute outside store, a spelling not in the Classify table, a non-canonical set).

## (5) What changes against option B

- B put one provider-level record behind the contract-query (FEAT bit 33), keyed by a kernel's `structure_key`. D is **per device** and has its own frames and bit; the contract-query is untouched.
- B listed dtypes per provider. D lets two devices of one backend differ, as the ruling asks. KISS-Contract is unchanged.
- Accuracy moves from "per backend" to "per device", and the kernel/device relation is a stated rule (§6.6-0010).
- **Consequence to review:** the Announce standard so far carries Classify and Contract content opaquely. The device record names Classify dtype tokens and Ops `MathFidelity` ordinals, so a reader validates them. The edge label in the Announce front matter ("OPAQUE") is not changed by this PR; whether it should be is for the maintainers.
- Limits of the record: ULP bounds only; relative and absolute bounds stay in the Contract Guarantees. KISS cannot verify that a device really computes what it claims, only that the claim is consistent (the negative controls).
